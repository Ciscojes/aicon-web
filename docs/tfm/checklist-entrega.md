# Checklist para convertir el borrador en entrega universitaria

## Datos institucionales pendientes

- [ ] Nombre completo del autor.
- [ ] Nombre oficial del máster.
- [ ] Universidad, facultad o escuela.
- [ ] Nombre del tutor o tutora.
- [ ] Convocatoria y fecha de entrega.
- [ ] Título definitivo aprobado.
- [ ] Plantilla institucional.
- [ ] Extensión mínima/máxima.
- [ ] Estilo bibliográfico obligatorio.

## Adaptación editorial

- [ ] Aplicar portada, tipografías, márgenes, numeración e interlineado oficiales.
- [ ] Generar índice general, de tablas, figuras y abreviaturas.
- [ ] Revisar resumen y abstract con el límite institucional.
- [ ] Convertir enlaces internos del repositorio en referencias/anexos estables.
- [ ] Numerar tablas y figuras y añadir fuente y texto alternativo.
- [ ] Exportar a PDF/DOCX y revisar saltos, enlaces y legibilidad.

## Revisión académica

- [ ] Confirmar con el tutor pregunta, objetivos y metodología.
- [ ] Validar que el término “Agentic Engineering Harness” se presenta como
      definición operacional del trabajo y no como estándar consolidado.
- [ ] Revisar originalidad y parafraseo; no entregar texto sin revisión del autor.
- [ ] Verificar cada cita y fecha de consulta.
- [ ] Incorporar reflexión personal del autor sobre decisiones y aprendizaje.
- [ ] Añadir agradecimientos y declaración de uso de IA si la universidad lo exige.
- [ ] Ejecutar la política institucional de integridad/plagio aplicable.

## Evidencia y privacidad

- [ ] Fijar commit o release exacto evaluado.
- [ ] Confirmar que CI y SonarCloud del commit final están aprobados.
- [ ] Comprobar que capturas no contienen clientes, claves, tokens ni correos reales.
- [ ] Mantener separados resultados académicos y preparación productiva.
- [ ] Documentar cualquier cambio de métricas posterior al corte de AEH-004.

## Defensa

- [ ] Adaptar el [guion](../agentic-engineering/demo-guide.md) al tiempo asignado.
- [ ] Preparar una demostración no destructiva o un video de respaldo.
- [ ] Ensayar preguntas sobre autonomía, seguridad, validez y generalización.
- [ ] Explicar claramente el caso real VERIFY → REPAIR.
- [ ] Cerrar con contribuciones, limitaciones y trabajo futuro.

## Información que necesito del autor

Para producir la versión institucional definitiva deben entregarse la plantilla
oficial y los ocho datos de la primera sección. No deben enviarse contraseñas,
tokens ni datos personales de clientes.
